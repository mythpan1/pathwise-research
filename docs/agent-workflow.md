# 学习型研究：Chat—执行者—Dot 协作闭环

本文件是当前协作流程的唯一主入口（2026-10-22）。项目仍在**学习型研究与流程试验**阶段：既检验思维实验方法，也检验协作方式；骨架会随真实问题演进，不以生产级架构、字段数量或自动化规模为目标。必要的记录服务于理解与复核，不是研究成果本身。

本轮仅完善流程文档，**研究仍暂停**。用户重新明确启动后才开展下一研究单元；写好规则、审核通过或合并均不自动恢复研究。

## 谁做什么，记录在哪里

- **用户**确定目标、授权边界和是否恢复研究，并手动唤醒 Chat 读取审核结果。
- **Chat（协调者）**每次只派发一个有边界的研究单元，写清问题、范围、输入、预期产物、方法、停止条件及执行者；读回实际产物，不把口头完成当成完成。
- **执行者**在独立分支完成该单元、自检并提交 PR；返工继续同一个 PR，不以新 PR 绕过问题。
- **Dot（审核者）**在明确交接后审核固定 head SHA，写回签名审核结论或返工清单；只有未参与编写该成果的实际审核运行才算独立审核。Dot 自己编写的成果须交给未编写者审核，不能签名自批。

Issue 是任务范围、负责人、依赖、预算/停止条件和验收的权威入口；PR 是候选差异、交接和返工讨论入口；`main` 是已采用版本。准备 Issue 前可用稳定的 `LOCAL-...` 标识，随后追加映射，避免两套状态。授权来自用户，不来自 PR 自报、标签或勾选。

继续遵守[参与者与步骤记录](agent-provenance.md)、[实验记录](experiment-protocol.md)及[审核记录](../reviews/README.md)的适用部分：记录真实执行者、规则版本、输入输出、实际操作与未知；不编造模型信息，不保存隐藏思维链。没有进行实验就不预填回合，不为凑字段制造证据。

## 一个研究单元的最小交付

在 Issue / PR 中用短段落或链接说明即可，不新增重型模板：

1. 要回答的具体问题与边界（地区、时期、对象），本单元不回答什么。
2. 假设、证据来源及方法：区分来源事实、假设、推断和待核实项；思维实验怎样推演、用什么观察区分解释。
3. 实际过程与结果：真正做了什么、改了什么、检查了什么；方法与计划的偏差。
4. 局限、反例、未完成和可改变判断的材料；实际产物及版本可追溯。

**负面结果、未得到确定结论也可以被采用**，只要问题、方法、过程和限制诚实且足以支持所述结果。不要为了通过审核拼出肯定结论。多个模型一致不等于验证；模型输出不能充当独立事实证据。形式完整不代替研究质量。

## 显式交接与状态

1. 执行中保持 Draft；普通提交、CI 成功或 PR 的 Ready 状态都不自动交给 Dot。
2. 执行者自检完成，由 Chat 或执行者在 **PR 正文**明确写入下面一行，填入真实完整 SHA 和交接者。将 PR 退出 Draft 后才进入待审；若工具无法退出 Draft，报告阻断，不能假称已交接。
   `ready for Dot review | head: <完整提交SHA> | handoff by: <Chat或执行者运行标识>`
   这只是清晰的人读标记，不是已安装的触发器，也不是批准。用户直接明确指定某 PR/SHA 交给 Dot 时，协调者可据实补录交接。
3. Dot 先重读当前 head 与任务边界；标记 SHA 不匹配、仍为 Draft 或仍在编写时不自动审核，先要求重新交接。
4. Dot 的 PR 签名评论写明：`Dot review | head: <完整SHA> | reviewer run: <实际运行标识> | verdict: 建议采用 / 需修改 / 证据不足`，附基线、审查范围、检查依据、未核事项、逐条阻断/非阻断问题及返工验收条件。签名是角色归属声明，不是密码学签名。
5. 用户手动唤醒 Chat，并让它读取该 PR 的审核。需修改时 Chat 指派执行者在同 PR 修订，逐条回应，更新完整 head SHA 并再次显式交接；Dot 复核变化及受影响的主张、证据和结论。
6. 通过后，满足下述合并门禁才可合并；下一单元仍由 Chat 在用户已明确启动和授权的范围内派发，不自动重启研究或无限延展任务。

不对未变版本反复审核。不因每4小时巡检就重复发同一审核；仅检查状态变化。新提交使原 head 的批准不再适用于当前 head，旧结论保留。基线变化或冲突解决影响已审内容时复核受影响部分；不能只看新增行而漏掉被推翻的结论。

## 审核归档与精确版本合并

PR 签名评论是即时反馈；按既有规则把实际审核归档到 `reviews/<任务号>-rN.md`，保留历史并链接原评论。冻结成果 H 后，仅追加真实审核记录 R 可由协调者提交，得到最终 head F；不得借归档夹带正文修改。合并者核对 H→F 仅有该记录且内容忠实，留下绑定 F 的最终核验评论。若还有任何其他变更，重新审核对应内容与受影响主张并绑定新版本。不得为在审核文件里写入包含自身的 SHA 而无限改提交。

用户已授权 Dot 对明确交接的 PR 写回审核，并在以下条件**全部满足**时合并，不需逐版再次请求用户批准：
- 在用户授权范围内，当前 head 有有效审核与最终核验；作者没有审核自己的成果。
- 无未解决阻断；非阻断项有明确处置；检查缺失、失败、运行中或不明均不得视为通过。
- 当前精确 head 上指定的 `.github/workflows/validation.yml` 成功，且平台要求的其他检查/批准均满足；无冲突，基线影响已核对。
- 合并前重新读取 head、base、检查及阻断状态，以预期完整 head SHA 执行合并；发生版本竞态则停止并重新核验。
- 尊重实际分支保护和平台限制，不能管理员绕过、降低门禁或假称存在/通过了无法读取的保护。历史“无保护”记录不代替合并时核验。

Chat、执行者和 Dot 可能共用同一 GitHub 身份。不同角色、模型或运行ID不证明不同账户，也不单独证明独立。若平台禁止正式自审，可用诚实的角色签名评论记录实际独立运行的研究审核；**评论不等于 GitHub APPROVE，也不能替代规则要求的独立账户批准**。缺该批准就保持未合并并报告；不切账号、改权限或绕过保护。

## 授权的流程，不等于已经自动接线

截至 2026-10-22：
- 当前实际定时任务仅为**每4小时只读检查并向负责人报告**，不写 GitHub、不合并、不触发 Chat。
- 用户新授权允许在明确交接后的实际任务中由 Dot 审核写回及条件合并；本文件记录这套操作规则，**不修改现有定时任务、不安装触发器**。
- 2026-10-19 取消的是旧周期协调/后台研究；10-22 的只读巡检不是恢复旧自动研究。用户仍需手动唤醒 Chat。
- 仓库已有[控制器与测试](review-automation.md)是另一条需本地登记和运行条件的实现，不表示它已在当前 Dot 流程运行；本任务不运行它、不调用 ACP、不操作凭据或账号、不启动实验。

## 并发、恢复与边界

继续使用独立分支和独立可写工作区，不直接推 main、不强推共享分支、不撤销他人成果。写入范围或依赖重叠的工作串行；共享受限工具遵守其串行约束。交接列出文件归属、依赖、工具、预算和停止条件；不因能访问而扩权。

中断先查实际提交、PR 和未结操作，再接续，不重复不明结果的写入。退回指工作状态退回，不删除历史；合并后纠错另开修复 PR。连续两轮仍未解决同一阻断时停止重复派工并交用户决策；预算/权限不足、范围扩大或身份条件无法满足时同样停在边界，不自行换入口绕过。无已授权且可推进任务就不启动 Agent。
