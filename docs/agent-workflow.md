# 多 Agent 协作与交接

状态：流程提案。先用 GitHub 原生任务与变更流程；尚未实现自动调度、自动审核或自动合并。

## 各种载体的职责

| 载体 | 权威内容 |
| --- | --- |
| Issue | 任务编号、范围、负责人、文件归属、依赖、预算、状态和验收；正文是任务书 |
| 独立分支与工作区 | 一项任务的可复现修改；多个执行 Agent 不共用同一可写工作区 |
| Pull Request（PR） | 这项任务的候选成果、差异、讨论及交接入口 |
| `reviews/` | 绑定具体版本的独立审核记录、问题、复核与未核范围 |
| `main` | 按流程完成审核并经项目负责人决定采用的版本 |

Issue 建立前可用[本地任务模板](../templates/research-task.md)准备。建立后以 Issue 正文为准，本地任务书只保留链接，不同时维护两份状态与范围。PR、审核记录引用任务编号，不复制任务状态。

仅本轮首次架构提案可用 `ARCH-001` 作为任务标识；后续研究与修改均关联 Issue，不继续使用这一例外。

## 角色与独立性

- 协调 Agent：拆解问题、锁定范围与文件归属、安排依赖、控制预算、处理交接。
- 执行 Agent：只修改分配文件，给出证据、成果和局限；完成自检后提交 PR。
- 审核 Agent：由单独的运行承担，未撰写本次被审成果，读取原始证据或明确未能核验；不替作者修改正文后再自审。
- 项目负责人：决定是否采用并合并。Agent 只有获得明确合并授权后才代为操作。

同一个模型可以承担不同任务；不同模型名称不能证明独立。记录 Agent 角色及可复查的运行标识，运行原始日志仍留本地。多个 Agent 可共用一个 GitHub 身份，但这不形成平台身份隔离，也不能伪装成不同人的批准。GitHub 不允许 PR 作者批准自己的 PR，见[官方说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)。独立审核记录与人的采用决定分别保留。

## 一项任务怎样流转

1. **待开始**：Issue 明确问题、输入、文件归属、验收、执行者、审核者、预算和停止条件。协调者分派；任何 Agent 不得自行扩展任务。
2. **执行中**：执行者从记录的基线提交建立独立分支及 worktree 或独立克隆。使用 `agent/<任务号>-<主题>` 等可辨认名称。只启动无依赖、写入范围不重叠的任务；预算在分派时核对，共享受限资源按其协议串行。
3. **待审核**：执行者自检并提交 Draft PR。交接写明基线、成果提交 SHA、修改文件、已完成、未完成、检查结果及下一步。只有仓库产物或可访问证据能作为交接依据，聊天中的“完成”不够。
4. **需修改 / 等待材料**：审核者将问题绑定文件和主张，说明影响及解决条件。作者逐项回应并修订；证据不足可收窄主张或保留未知，不强行补齐结论。
5. **待采用**：独立审核建议采用、阻断项关闭，合并者核最终差异及审核覆盖后，将 PR 标记为可审阅并等待负责人的采用决定。
6. **已采用 / 已终止**：负责人决定并合并后关闭 Issue；终止则记录原因和未用产物，不把已上传或已生成文件算作采用。

任务阻塞或 Agent 中断时，协调者保留最后提交、剩余工作和阻塞原因，明确撤销原写入归属后再转派。重跑先检查已有分支和 PR，避免重复交付。Agent 之间可以提问或提供反证，但变更范围和归属由协调者更新 Issue。

## 并行、冲突和新版本

任务写入范围不同仍可能有语义依赖，须显式记录。依赖未完成时只做不依赖它的工作，不将上游草稿视为定论。各 Agent 不覆盖他人工作，不直接推 `main`，不强推共享分支。

多个 PR 修改同一文件或同一结论时，协调者决定整合顺序，作者在自己的工作区处理冲突。基线变化、合并冲突解决或研究正文修订后，审核者复核新增差异及相关结论，记录新的提交 SHA；不能沿用旧版结论冒充新版本已审。

## 当前技术边界

以上是仓库流程约定。模板、Markdown 审核记录及 `.gitignore` 都不是权限或合并门禁。本次未配置自动检查、CODEOWNERS、分支保护或 ruleset，也未启动后台 Agent。机械检查只能核文件、链接和格式，不能代替政策原文或因果判断的审核。

以后需要技术强制时，再核验仓库套餐、身份及绕过权限，配置 PR 要求和真正存在的检查。私有仓库分支保护的适用套餐见[GitHub 官方文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。不因需要多 Agent 而先创建多个账号，也不把仓库访问凭据写进任务或日志。
