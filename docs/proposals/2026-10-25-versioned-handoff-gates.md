## 1. 解决的问题与成功标准

核心目的：政策、产业变迁、人口结构变化三条主线，连续服务中国未来十年的学业／职业选择及当前志愿和培养路径。国际环境仅作具体相关背景。此定义来自用户2026-10-25明确决定；PR70仍待采用，不能假称main已经完成定义同步。

要防止的不是“文字不够详细”，而是：方向经摘要转述发生漂移、交接材料遗漏或换版、旧审核用于新正文、阶段交付无人接续、合并后导航仍停在历史状态。验收必须证明错误被拦住、正常路径能结束、中断能恢复，不能以文档数量或PASS文件数衡量。

三个概念分开：
- **合格交接**：接收了规定的同一批字节，并了解缺口。
- **内容审核**：推理、事实使用和项目方向是否合格。
- **采用**：满足条件后成果真正进入main并完成读回。没有授权下一任务就停止。

## 3. 一个任务、一份权威状态、分开的历史

Issue是人读入口，不把可编辑Issue文字当不可变授权。任务批准时保存冻结任务书，得到task_revision与sha256，并将批准范围和来源绑定到执行者不能自行改写的协调记录。PR只是候选，不授予权限。

最小记录：
1. charter_ref：核心目的、三主线、阶段边界的固定版本。
2. task_ref：任务编号、问题、主线归属、允许路径/行动、预算与停止条件、交付清单、负责人及批准来源。
3. handoff_manifest：阶段输入输出文件和摘要说明；字节校验清单。
4. receipt：接收者实际校验结果、缺失项、承接责任与下一动作。
5. review_record：被审内容版本、范围、真实审核者、结论/阻断与来源映射。
6. adoption_record：最终版本、门禁、实际合并结果与main读回。

这些是逻辑记录，不强制六个独立文件或六次提交；可以在一个任务记录中分段。权威状态由已验证事件推导，README只展示当前状态及历史链接，不另维护第二套真相。

初始不安装自动调度；必须选定真实运行宿主、持久存储、谁负责唤醒和停机恢复后，才允许声称自动接续已实现。模型回复结束不是后台工作仍在进行。

## 4. 哈希交接契约

哈希用于字节一致性，不证明真实性、完整理解或发送前未删减。任务书规定“应交什么”，清单列“实际交什么”，内容审核检查语义。

### 4.1 清单和可信锚点

每个条目至少记录 artifact_id、role、repo/受控位置、固定commit、相对path、原始字节数、sha256、media_type、evidence_status、derived_from。任务可有必需及可选条目；可选缺失也必须说明，必需缺失不许悄悄省掉。

路径和hash来自实际读取，不手填猜测；规范化相对路径、拒绝路径逃逸和重复artifact_id。默认不接受符号链接或子模块当普通证据文件；确需使用时另列对象与授权边界。缺失、额外的未授权产物、大小或hash不符均阻断。单个文件过大时分块索引与完整哈希同时保存，接收者按任务需要实际取回，不把上下文截断当完整交付。

清单不写自己的hash，也不写包含自身的新commit，避免自引用。先提交文件与清单得到C1，再由受信协调记录绑定C1、清单路径和清单sha256；接收凭据另存C2或仓库外账本。检验顺序：
可信锚点 → 精确清单字节 → 文件全集 → 每项字节/hash → 实际可读范围 → 内容承接。

接收者不能仅相信发送者提供的hash。若清单与文件一同被替换，与受信C1/清单hash不符仍须失败。受信锚点不能只在同一可改PR里自我声明。

### 4.2 字节和版本规则

SHA-256按保存的原始字节计算，不先去空格、改换行或重排JSON。需要规范化时产出新文件，保留原文件、转换规则、工具版本及derived_from；规范化产物不能冒充原件。Git commit/blob标识用于定位仓库对象，不把Git对象hash与文件SHA-256混为一谈。

网页解析文本与HTML/PDF原件分别标类型。一次工具返回片段只能证明保存了该片段，不得称完整原文。视频字幕抽样、摘要、翻译和分析均为派生材料。接收者访问不到受控原件时，写limited_receipt，依赖该原件的核查不得标完成；可缩小经授权的验收范围，但不能自动丢弃证据继续。

含个人信息或凭据的材料不因清单要求被上传；仓库仅保存获准索引/必要摘录。哈希不是加密，不公开敏感低熵字段的可猜测hash。文件留存、权限和引用可达性需分别核查。

## 5. 状态与四道关口

状态：PLANNED → RUNNING → DELIVERED → REVIEWING → APPROVED → MERGING → ADOPTED。
返工回RUNNING并生成新revision；PAUSED/BLOCKED可发生在任意未完成状态；每次必须有原因、负责人和恢复条件。CLOSED/CANCELLED保留历史，不自动恢复。没有收到回执不能据沉默标完成。

| 关口 | 机器检查 | 人的/模型的内容判断 | 不通过 |
| --- | --- | --- | --- |
| G0开工 | 授权、task/charter版本、范围、必要输入/接收凭据、预算和停止条件齐备 | 为什么做、连续研究链位置、预计改变什么选择判断 | 缺字段默认阻断，不自动补授权 |
| G1交付 | 必需产物全集、manifest可信锚点、接收者重算、引用/版本、范围及失败记录 | 事实/假设/推断边界与关键问题是否覆盖 | 返回缺口，不靠文件存在判合格 |
| G2审核 | 固定成果及输入、审核身份/来源、作者分离、阻断状态 | 逻辑、证据适用性、主线及决定来源；反证是否保留 | 明确问题与受影响范围，原PR返工 |
| G3采用 | 当前精确head/base、有效审核、最终差异、CI和平台门禁、授权、幂等锁 | 不重新代替G2裁决；异常交回 | 不合并，保留待采用状态 |

一项任务可以纯整理或条件推演；不得为了过关强制新搜索。证据不足不必全部补齐：能交明示条件结论时，按批准范围接受；关键逻辑断裂或把未核当事实才阻断。

方向变更须单列决定：原定义、变更理由、用户批准来源、影响范围和生效版本。普通作者不能以“用户已明确”的编辑摘要替代原始决定；新任务遇到过期方向版本先对齐，不静默迁移所有历史内容。

## 6. GitHub衔接，不逐阶段合并

同一Issue/PR内可以依次提交收集C1、分析C2、返工C3；分析记录明确消费C1的清单。多个收集运行分别交manifest，由协调者做有来源映射的合并清单，不以短摘要取代输入。无新收集任务直接复用既有固定输入，不空转角色。

G2绑定正文H及其任务/输入/规则版本。审核后F仅增加真实审核归档时，核H→F所有提交与完整差异，只允许预定审核记录路径，验证评论/回执来源及归档内容；不递归审核归档本身，不允许夹带正文。多次归档勘误需明确更正范围并保持真实来源，不能只检查最后一个commit。

正文、输入或规则有实质变化：只重审受影响内容及依赖，不让旧approve自动继承。main前进：先做差异影响检查；无关新增不强制重写全文，有冲突或影响假设/引用/规则时针对性复核。最终检查绑定真实采用组合，不把旧base上的成功等同新组合测试成功。

G3立即重读head、base、有效审核和检查，以expected head普通合并。若平台不能原子绑定base，则不得称完全消除了竞态：需采用受控串行队列/平台可用的受保护合并队列，或接受显式记录的协作级残余风险；需要更强保证却无能力时阻断而非绕过。合并未知先查PR、main及提交关系，不重发不明写操作。

合并后读回merge SHA及预期文件，生成采用收据，再更新当前导航；导航更新失败记ADOPTED_NAV_PENDING，内容已采用但收尾未完，补导航不能重做合并。最终报告交付/审核/采用三态，不笼统说“完成”。不自动关闭未解决的证据Issue，不启动下一研究。

## 7. 信任边界与接线等级

仓库内文件、PR标签、作者提交的review JSON或不同run_id都可以自填，不能独立作为批准来源。协调者必须从实际已授权审核会话/身份或受信服务回执核对被审版本及作者分离。评论可归档，但同一账号发的评论不等于GitHub独立账户APPROVE。未来若用签名，须先有受保护的密钥和身份登记；签名仅证明来源，不证明内容正确，本设计不创建密钥。

三个等级必须据实命名：
- L0文档协作：检查由人/Agent遵守，可能绕过；当前方案未部署，不能宣称已达L1。
- L1受控调度与校验：启动器和采用器拒绝无凭据操作；仍有直接push/merge入口时只是受控入口内强制。
- L2服务端强制：具备可用分支保护/required checks及受限写入权限，明确管理员/绕过范围，并测试其他入口也不能越过。若计划或权限不支持，保留L1和限制，不把红叉CI叫硬门禁。

校验器自身必须取自受信固定版本，候选PR不能同时改掉检查器并证明自己通过。解析候选资料视为不可信数据，使用安全解析，不执行候选脚本。检查流水线默认只读、无秘密；合并权限与不可信内容执行分离。避免用高权限pull_request_target去checkout执行候选内容。规则/validator改动需要单独评审后更新受信版本，普通研究PR不能自降门槛。

GitHub保护能力与计划、配置有关，需实施前实测，不能凭本设计保证。依据：[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Actions安全](https://docs.github.com/en/actions/reference/security/secure-use)。本次读取发现的计划限制不是永久结论；不通过公开私库、改权限或换账户规避。

## 8. 恢复、预算与停止

每个外部操作先记operation_id、任务revision、目标、预期版本与意图；后记真实结果。状态转换使用版本号compare-and-swap及每任务/采用队列锁，重复事件只确认不重复执行。过期worker回执不能覆盖新revision。租约到期不等于旧worker已停止，必须核对或隔离其写入后再接管。

网络失败、超时、空返回与拒绝分开记录。失败路径也必须留下事件；不能依赖脚本最后一段才记录失败。无持久记录能力时停止写操作。结果未知进入RECONCILE，不改称失败重做，也不把所有已合并任务退回Draft。

额度按任务记录实际调用与失败，不反复查询余额。额度策略、限流与账号切换沿现有已授权协议，本设计不改变它们。无法核实预算边界就报告，不把未知写成耗尽。

每个待处理状态都有owner、next_action、等待原因及下一检查触发。调度器完成一个阶段后读回并推进已授权下一阶段；若运行宿主已结束，不声称持续监控。自动唤醒/固定周期监控需另行授权及验证，不复活已停四小时任务。

## 9. 原故障注入验收设计（历史计划，非全量实测结论）

| 注入 | 预期结果 |
| --- | --- |
| task/角色/范围字段缺失 | G0阻断，有明确缺项事件 |
| 缺一个必需文件，其他hash正确 | G1阻断，指出缺失artifact |
| 文件与清单同时替换 | 与受信C1/清单锚点不符而阻断 |
| 换行或字节改变 | 原字节hash失败；显式转换产物走新版本 |
| 工具输出截断／受控输入不可读 | limited_receipt，不声称完整核验 |
| 作者自填不同reviewer_id | 无受信审核回执，G2不通过 |
| 方向变更夹在普通报告 | 内容审核标阻断，需独立决定；机器只能检测标识，不能保证语义识别 |
| 审核后改正文／依赖规则 | 旧审核失效，针对性重审 |
| 只加真实审核归档／再勘误 | 检查全tail及来源，通过后不递归内容审核 |
| PR修改validator使自测常绿 | 不采用PR内validator的自证结果 |
| main变化／merge时版本竞态 | 重新核对组合；缺原子保障明确降级或阻断 |
| merge返回超时但实际成功 | 查询确认一次，不能二次合并 |
| 收到重复/过期回调 | 幂等处理，不覆盖新状态 |
| merge成功但导航写失败 | ADOPTED_NAV_PENDING，不把内容当未合并 |
| 直接绕过受控入口尝试合并 | L2应由服务端拒绝；若成功则不可标L2 |
| 正常有限任务 | 经过四关口到已采用或明确阻塞，无多余搜索/重复审核 |

每个测试保留实际输入、预期、观测、版本和副作用。不能预填PASS。测试只在另获批准的隔离试验范围执行；不对生产main做破坏性演练。

## 10. 最小实施候选与本次停止点

先实现可离线验证的manifest/receipt与纯状态转换，再做模拟故障测试，随后才考虑只读影子校验、受控开工/采用入口、服务端保护。每阶段必须分开授权、实现及验收，不因设计获审自动部署。

现有控制器可复用评估/恢复骨架，但需补可信凭据验证、受影响base检查、多提交归档tail、采用后导航状态；具体实现由后续任务另定。不直接把本稿当成已修改代码或新现行工作流。

本次只交设计并开独立审核。审核重点：是否真能发现遗漏/换版，谁能伪造凭据，主线语义检查由谁负责，权限覆盖能否兑现，恢复是否幂等，是否过度增加步骤。评审结论需区分设计合理性与运行验证。审核结束向用户报告；不自动合并、部署或更改PR32/70。
